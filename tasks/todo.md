# v3.0.0 -- Multi-template architecture

## Goal
Replace the single flat `templates/` directory with a named-template system.
Each template is a self-contained folder under `templates/` with a `project/`
subtree (copied to project root) and a `claude/` subtree (installed into `.claude/`),
plus a `git-hooks/` subtree (installed into `.git/hooks/`). A `templates/.default`
file names the default template. `bootstrap.sh` becomes a walker, not a file-by-file
copier. New interactive template selection prompt at mkproj run time.

## Deferred (v3.x)

- [ ] `mkproj --prune` -- detect and offer to delete optional template files that have never
      been modified since install (current_hash == installed_hash AND tier == optional).
      Uses existing .mkproj registry hashes; no content scanning needed. Interactive by default,
      --yes for non-interactive. Leaves folders intact (they may be waiting for content).
- [ ] `--update --components=hooks,rules` selective component updates
- [ ] `--max-depth N` for scan depth control
- [ ] `--force` flag (requires audit trail before overwriting user edits)
- [ ] Component-level options in `--adopt`
- [ ] `--json` machine-readable output for scripting
- [ ] `mkproj --init` alias for the default bootstrap mode
- [ ] `mkproj --diff NAME` -- show pending changes without updating
- [ ] Windows native support (WSL2 recommended in the interim)
- [ ] settings.json is generated by generate_settings_json() in bootstrap.sh rather than
      copied from a template. This prevents pre-bootstrap customization of default hook
      config and timeouts. Consider moving to a template file with macro substitution,
      consistent with how other infrastructure files are handled.
- [ ] `mkproj diagnose` hook diagnostic: enumerate all hooks in ~/.claude/settings.json
      (global + project), run each with a hard timeout, record exit code/duration/stderr,
      label each result as PB-owned / user-defined / third-party plugin, and produce a
      plain-text report. Example output: "Stop hook 2/6: mempalace hook run -- TIMED OUT
      (10s) -- source: global settings.json, not PB." The claude-mem bun-runner (exit 1,
      52ms) is the reference test case to validate against.
- [ ] Move configurable timeouts out of hardcoded values and into a config file (e.g.
      mkproj.conf or a [timeouts] section in .mkproj). Timeouts appropriate for a fast
      local machine may be too tight on a slow system or over a network mount.
- [ ] Dynamic timeout suggestions: when `mkproj diagnose` observes a timeout, suggest a
      concrete config change to the user based on the observed duration. Example: "hook
      took 8.2s before timeout -- consider raising hook_timeout_stop to 15 in mkproj.conf."
      Avoids static "try increasing the timeout" advice that ignores actual performance.
